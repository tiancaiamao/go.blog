# go.blog

Static blog generator for [tiancaiamao.github.io](https://github.com/tiancaiamao/tiancaiamao.github.io),
written in [TA](https://github.com/tiancaiamao/tinyactor) and run on the tinyactor VM.

`content/*.md` (Markdown posts) → HTML pages, category/tags/archive index pages and
the Atom feed, written to `generate/`. `generate` is a symlink to the published-site
checkout (`../tiancaiamao.github.io`), so a rebuild edits that repo; it is
`.gitignore`d and never committed here.

## Requirements

- `tinyactor` toolchain, pinned by commit in `tinyactor.deps`:

  ```
  tinyactor	git+https://github.com/tiancaiamao/tinyactor	<pinned sha>
  ```

  `tinyactor.lock` records the resolved sha. Fetch the sources with
  `tinyactor vendor` (creates `vendor/tinyactor`), then build once:

  ```
  make -C vendor/tinyactor
  ```

  `blog-gen-ta` does that build itself on first use. The vendored clone carries
  sources only — `tavm` and the `lib/*.dylib` C modules are build products and are
  not tracked by tinyactor.
- a C compiler (for `tavm`, the stdlib modules, and this repo's `lib/md4c.dylib`).

## Usage

```
./blog-gen-ta generate                    # full rebuild of every page
./blog-gen-ta file 2024-01-15-my-post.md  # one post + index/category/tags/feed
./blog-gen-ta help
```

The wrapper runs the generator exactly once and only rsyncs
`resources/public/static/` into `generate/static/` afterwards — a failed or
partial generation never gets static assets copied over it.

### Toolchain resolution

1. `$TINYACTOR` — explicit override
2. `vendor/tinyactor/tinyactor` — the pinned toolchain
3. `tinyactor` on `PATH`
4. `../tinyactor/tinyactor` — a sibling checkout

To generate against a local tinyactor checkout you are editing, make it explicit:
`TINYACTOR=../tinyactor/tinyactor ./blog-gen-ta generate`. Do not leave such a
setting in `tinyactor.deps`; local `file://` sources are for development only.

`blog-gen-ta` also refuses to run when `vendor/tinyactor` is not at the sha in
`tinyactor.lock` (`tinyactor vendor` fixes it), so a stale clone cannot silently
build the site against a different stdlib.

## Layout

```
content/           Markdown posts + content/index.json (metadata index)
template/          page templates (about/home/project)
resources/public/  static assets, synced into generate/static/
dsl/              template DSL compiler + templates.dsl (page/feed templates)
src-ta/gen.ta      generator entry point
src-ta/lib/        core (page assembly), generated template stubs, md, md4c (C glue)
src-ta/md4c/       md4c glue.c -> lib/md4c.dylib
src-ta/test/       .ta test suites + core_test.sh / template_test.sh / wrapper_test.sh
tools/build-dsl.sh DSL -> KL + TA entry -> one runnable KL image
blog-gen-ta        wrapper: build, generate, sync static
tinyactor.deps     dependencies (pinned tinyactor commit)
tinyactor.lock     resolved dependency shas (generated by tinyactor vendor)
```

## Tests

```
tinyactor run src-ta/test/html_test.ta       # tinyactor:lib/html    vs baseline
tinyactor run src-ta/test/md_test.ta         # markdown -> sxml rep
src-ta/test/template_test.sh                 # template DSL constructors (combined KL)
src-ta/test/dsl_test.sh                      # DSL sugar (backquote/splice/def)
tinyactor run src-ta/test/json_test.ta       # stdlib json
src-ta/test/core_test.sh                     # full page set, byte-identical
src-ta/test/wrapper_test.sh                  # blog-gen-ta behaviour
```

`core_test.sh` and `wrapper_test.sh` byte-compare against `generate/`, so the site
must be generated (and current) before running them. Markdown/template expectations
under `src-ta/test/baseline/` are golden fixtures checked against the generated site;
the table expectations (`raft-2F1A`, the `table` fixture) are TA-generated because
the old renderer had no tables support (`MD_FLAG_TABLES`).

## History

The generator was previously written in Clojure and then in cora; both are gone.
The current implementation is TA (`src-ta/`, driven by `blog-gen-ta`), with the
page/feed templates written in the in-repo DSL (`dsl/templates.dsl`) and compiled
to KL + TA external stubs by `tools/build-dsl.sh`. The TA core consumes the
resulting Node trees. Output is byte-identical to the golden fixtures and the
`generate/` tree, including `feed.atom`.
